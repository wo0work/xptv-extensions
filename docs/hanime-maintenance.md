## 原问题和排查经过

1. 原脚本可以显示封面和标题，播放器一直加载、时间停在 00:00，最初截图只有很低的请求速度，没有明确错误提示。其他源可以播放。
2. 用户确认相同手机浏览器能正常播放 watch?v=407593，因此不能直接认定视频失效或全部网络不可达。
3. 调试曾出现 undefined is not an object (evaluating 'ext.url')，修复方向是统一参数格式、接受对象或 JSON 字符串，并校验 ext.url。
4. 诊断脚本曾显示 Cloudflare 防护提示；用户确认 XPTV 的“自动过 CF”已开启。
5. 曾把页面包含 Cloudflare 脚本当作被拦截证据，这是误判。正常视频页也可能包含相关脚本。应结合页面标题和实际视频节点判断，不能只匹配 challenge-platform 等字符串。
6. 用户切换日本分流后主页也无法刷新。本次没有证实站点固定屏蔽哪些地区的 IP，不能把这次结果当作区域封锁结论。
7. 订阅拉取曾失败，用户更倾向直接导入 JS 文件。曾用固定单视频诊断脚本 v5、v7、v8、v9 排查。文件名和内容版本一度不一致，因此判断版本应看脚本内容，不能只看文件名。
8. v8 未取得 contentUrl，但页面标题显示实际视频信息。仅依赖 JSON-LD contentUrl 的解析不够。
9. v9 优先读取 video/source 标签，取得媒体地址；诊断显示媒体服务器 vdownload.hembed.com，用户明确确认“这一版可以正常播放了”。

## 当前代码行为

### 播放解析

- normalizeHanimeArgs 接受对象或 JSON 字符串；无效 JSON 明确报错。
- 请求详情页时发送 User-Agent 和 Referer。
- 候选地址优先级：video[src] / video source[src]，其次 JSON-LD contentUrl，再其次播放器脚本中的媒体地址。
- video/source 的合法 HTTP(S) 地址不强制要求 URL 以 .mp4 结尾；脚本配置兜底要求 mp4 / m3u8 / webm 扩展名，以减少误识别。
- 拒绝 blob、data、javascript 等无法直接交给播放器的地址；规范化相对地址。
- 返回 urls 和对应 headers；播放请求 Referer 是当前详情页。
- 未取得地址时给出诊断信息，不把详情页 HTML 当作视频链接。
- Cloudflare 判断仅是诊断，不是保证通过挑战的方案。没有实现独立 CAPTCHA 绕过或跨浏览器 Cookie 共享。
- 实机已确认成功的是 v9 的 video/source 路径；后续维护应优先保留这条路径。

### 剧集提取（v11）

- 请求当前详情页，读取 #playlist-scroll > div。
- 链接优先取行的 data-href，兼容 .video-title a、a.overlay 和行内 watch 链接。
- 标题使用 .video-title，兼容旧版 .card-mobile-title。
- 按视频 ID 去重，避免桌面与移动端两份清单重复。
- 保持网站的清单顺序（已检查示例为最新集在前）。
- 只提取清单，不扫描相关影片推荐，避免把其他作品混入系列。
- 清单没有当前视频时补回当前视频；请求失败仍返回当前视频供播放解析重试。
- 未过滤清单里的预告片；条目名称沿用网站。
- 目前读取详情页已有清单，没有抓取完整清单页或翻页。若将来发现详情页只提供部分剧集，需要根据实际页面补全。

## 下次排查建议

1. 先确认实际加载的版本、导入方式与可复现详情页；本地导入和远程订阅的缓存行为不同。
2. 读取仓库当前代码；本记录可能落后于后续提交。
3. 对比实际返回 HTML、标题、清单节点和 video/source，不根据低速截图单独判断原因。
4. 如果只有一集，区分：旧版缓存、清单请求失败、选择器变化、详情页清单被截断。
5. 如果有全部剧集却无法播放，检查选中条目的 ext.url、解析候选地址和播放请求头；不要先改已成功的解析路径。
6. 修改后检查语法及相关边界，记录验证结果；等待用户实机反馈后再标记已验证。
7. 用户曾明确要求把修正脚本更新到本仓库方便远程拉取。后续会话仍应根据当时用户请求确认实际修改范围，本文不授权任意发布操作。
